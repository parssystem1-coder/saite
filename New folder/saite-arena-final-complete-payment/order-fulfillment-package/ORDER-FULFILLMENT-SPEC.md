# مشخصات حرفه‌ای عملیات سفارش، بسته‌بندی و ارسال

## هدف

صفحه سفارش فقط نباید بگوید «سفارش تایید شد». باید اپراتور را از تایید تا آماده‌سازی، چاپ برچسب، تحویل به شرکت حمل و رهگیری مرسوله هدایت کند.

## تصمیم طراحی

- **Drawer جزئیات** به‌جای رفتن به صفحه جدا: اپراتور context فهرست را از دست نمی‌دهد.
- **Stepper چهارمرحله‌ای**: ثبت سفارش، پرداخت، بسته‌بندی، ارسال. مرحله فعلی واضح است.
- **هشدار قبل از تایید**: آدرس و ارزش مرسوله داده‌های حساس و مسئولیت‌زا هستند.
- **پیش‌نمایش لیبل**: قبل از چاپ، دقیقاً همان چیزی که روی بسته می‌رود دیده می‌شود.
- **فیلدهای گروه‌بندی‌شده**: گیرنده، اقلام، بسته، حمل. فرم شلوغ و یک‌تکه نیست.
- **Responsive واقعی**: در موبایل drawer تمام‌صفحه می‌شود و جدول هنوز قابل اسکرول است.

## فیلدهای لازم برای برچسب و ارسال

### گیرنده

- نام و نام خانوادگی یا نام شرکت
- شماره تماس اصلی
- آدرس کامل شامل استان، شهر، منطقه، خیابان، کوچه، پلاک و واحد
- کد پستی ۱۰ رقمی
- شناسه سفارش برای تطبیق بسته

### اقلام و بسته

- نام کالا، مدل و تعداد
- وزن تقریبی هر قلم
- تعداد بسته
- نوع بسته: کارتن مقاوم، شکستنی، پاکت حباب‌دار یا سفارشی
- ابعاد بسته
- وزن نهایی
- ارزش اظهارشده مرسوله
- وضعیت برچسب شکستنی
- قرار گرفتن فاکتور داخل بسته
- فعال بودن بیمه مرسوله

### روش ارسال

- شرکت حمل
- نوع سرویس و زمان تحویل تخمینی
- کد رهگیری
- هزینه ارسال و پرداخت‌کننده آن
- یادداشت داخلی انبار و ارسال

## پیشنهادهای اضافه‌شده از طرف من

1. **جداسازی ارزش سفارش و ارزش اظهارشده**: این دو همیشه یکی نیستند. ارزش اظهارشده برای بیمه و مسئولیت حمل است.
2. **وزن و ابعاد اجباری قبل از چاپ**: هزینه ارسال و ظرفیت شرکت حمل به این دو وابسته است.
3. **ثبت بسته‌های چندگانه**: سفارش بزرگ ممکن است چند بسته داشته باشد و هر بسته کد رهگیری جدا داشته باشد.
4. **قفل کردن اطلاعات پس از چاپ**: بعد از چاپ برچسب، تغییر آدرس باید با ثبت دلیل و کاربر انجام شود.
5. **audit trail**: ذخیره کند چه کسی، چه زمانی، وضعیت را به بسته‌بندی یا ارسال تغییر داده است.
6. **کنترل صحت کد پستی**: در اتصال واقعی، API شرکت پست یا سرویس اعتبارسنجی باید استفاده شود.
7. **محاسبه ارزش از سرور**: مبلغ و ارزش کالا هرگز از localStorage یا ورودی کلاینت معتبر تلقی نشود.
8. **عدم نمایش کامل اطلاعات در لیست**: آدرس کامل فقط داخل drawer مجاز نمایش داده شود.
9. **چاپ دوباره با watermark**: برچسب reprint باید مشخص کند نسخه دوم است تا دوبار ارسال نشود.
10. **اعلان وضعیت به مشتری**: بعد از ثبت کد رهگیری، پیامک/ایمیل/اعلان داخل حساب کاربر ارسال شود.

## قواعد امنیتی و صحت داده

- مبلغ نهایی، اقلام، موجودی و ارزش سفارش از سرور خوانده شوند.
- دسترسی endpointهای سفارش فقط برای نقش admin باشد.
- تغییر آدرس و چاپ برچسب audit شود.
- کد رهگیری validate و escape شود.
- اطلاعات شخصی در URL، log عمومی یا localStorage ذخیره نشود.
- پاسخ صفحه و endpoint ادمین `Cache-Control: no-store` داشته باشد.
- برای خروجی CSV، injection سلول‌های Excel با escape مناسب بسته شود.
- در محیط production، چاپ برچسب بدون تکمیل فیلدهای ضروری ممکن نباشد.

## اتصال به پروژه فعلی

در وضعیت فعلی `src/app/admin/(panel)/orders/page.tsx` فقط `AdminModulePage` و placeholder دارد. برای اتصال واقعی:

1. کامپوننت client برای جدول، فیلتر و drawer بسازید.
2. `getAdminSession()` را در Server Component یا Route Handler نگه دارید.
3. adapter جدا برای `getOrders`, `getOrderById`, `updateFulfillment`, `printLabel` تعریف کنید.
4. ابتدا mock adapter را با همین قرارداد بسازید.
5. بعد API و دیتابیس را بدون تغییر UI جایگزین کنید.
6. برای چاپ، endpoint سرور باید برچسب را با داده تاییدشده تولید کند.

## معیار پذیرش

- اپراتور از لیست می‌تواند جزئیات یک سفارش را بدون ترک صفحه باز کند.
- آدرس کامل، کد پستی، تماس، اقلام و ارزش مرسوله در دسترس است.
- نوع بسته، وزن، ابعاد، بیمه و شکستنی ثبت می‌شود.
- روش ارسال و کد رهگیری ثبت می‌شود.
- پیش‌نمایش چاپ با داده فرم هم‌خوان است.
- ثبت وضعیت بعد از تایید، قابل audit است.
- سفارش بدون آدرس یا کد پستی معتبر قابل چاپ نیست.
- موبایل و دسکتاپ هر دو قابل استفاده‌اند.
