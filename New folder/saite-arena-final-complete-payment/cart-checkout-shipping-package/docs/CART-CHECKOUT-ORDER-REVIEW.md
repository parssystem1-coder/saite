# بازبینی و بازآرایی سبد خرید تا سفارش و لیبل پستی

## یافته‌های مهم در کد فعلی

1. `CheckoutClient` فقط به `useAuthStore` کلاینتی تکیه دارد. این store در localStorage است و نباید مرجع امنیتی یا هویت سفارش باشد.
2. ثبت سفارش فعلی با `setTimeout` شبیه‌سازی می‌شود و `totalPrice()` کلاینت را ذخیره می‌کند. این مبلغ قابل دستکاری است و باید در سرور دوباره قیمت‌گذاری شود.
3. فرم فعلی نام، موبایل، استان، شهر، آدرس و کدپستی دارد، اما مدل واحدی برای آدرس قابل چاپ و آدرس ذخیره‌شده وجود ندارد.
4. روش ارسال هنوز در checkout ثبت نمی‌شود، پس پنل سفارش نمی‌تواند از checkout شرکت حمل و سرویس واقعی بگیرد.
5. `last-order.ts` فقط metadata سبک نگه می‌دارد و برای صفحه موفقیت خوب است، اما نباید جای سفارش واقعی backend باشد.
6. ورود به `/checkout` باید به ثبت‌نام یا ورود منتهی شود، اما بعد از login باید redirect داخلی و حفظ cart انجام شود.
7. آدرس کامل نباید در URL یا localStorage خام ذخیره شود؛ فقط در سفارش سرور و در صورت انتخاب کاربر در address book حساب ذخیره شود.

## جریان پیشنهادی نهایی

### مرحله ۱، سبد

- نمایش اقلام، تعداد، قیمت نمایشی و وضعیت موجودی.
- هشدار صریح برای قیمت یا موجودی تغییرکرده.
- CTA تکمیل خرید.
- اگر کاربر وارد نیست: `/login?redirect=/checkout`.
- ادامه خرید باید همیشه آزاد باشد و نیاز به ثبت‌نام نداشته باشد. اجبار ثبت‌نام فقط برای ورود به پرداخت و ثبت سفارش است، نه برای browsing.

### مرحله ۲، هویت و آدرس

- کاربر یا ثبت‌نام می‌کند یا وارد می‌شود.
- نام گیرنده، موبایل، استان، شهر، آدرس کامل، پلاک/واحد و کدپستی ۱۰ رقمی.
- گزینه «ذخیره این آدرس برای خرید بعدی» با رضایت کاربر.
- آدرس‌های ذخیره‌شده قابل انتخاب، ویرایش و حذف باشند.
- قبل از ادامه، پیش‌نمایش آدرس چاپی نشان داده شود.

### مرحله ۳، ارسال

- انتخاب پست، تیپاکس، چاپار یا پیک، بر اساس مقصد و محدودیت کالا.
- نمایش زمان تخمینی تحویل و هزینه.
- هزینه ارسال و بیمه باید از سرور بیاید.
- برای چندبسته‌ای، تعداد بسته و بازه هزینه/زمان نمایش داده شود.

### مرحله ۴، پرداخت

- خلاصه نهایی شامل اقلام، تخفیف، ارسال، بیمه، مبلغ قابل پرداخت.
- سرور دوباره cart را با id و quantity می‌خواند، قیمت و stock را verify می‌کند، order snapshot می‌سازد و سپس به درگاه می‌رود.
- بعد از callback درگاه، سفارش فقط با نتیجه تاییدشده paid شود.

## قرارداد داده پیشنهادی

`CheckoutOrderDraft` در `src/types/checkout-order.ts` شروع قرارداد است. در backend باید به Order Snapshot تبدیل شود:

```ts
{
  orderId,
  customerId,
  lines: [{ productId, sku, nameSnapshot, quantity, unitPriceSnapshot }],
  shippingAddressSnapshot,
  shipping: { carrier, service, cost, insurance, packageCount },
  payment: { method, status, authority, paidAt },
  totals: { subtotal, shipping, discount, insurance, grandTotal },
  fulfillment: { status, packages: [] },
  audit: [{ actorId, action, at }]
}
```

## پیشنهادهای حرفه‌ای

- آدرس سفارش snapshot شود، چون مشتری ممکن است بعداً آدرس پروفایلش را تغییر دهد.
- نام، SKU و قیمت کالا در snapshot ذخیره شود تا فاکتور تاریخی خراب نشود.
- کد پستی با schema کلاینت و سرور validate شود.
- از localStorage فقط برای cart lineهای غیرحساس استفاده شود، نه قیمت معتبر، آدرس یا وضعیت پرداخت.
- پرداخت idempotent باشد تا refresh callback سفارش تکراری نسازد.
- قیمت و موجودی در checkout lock کوتاه‌مدت یا هنگام create order دوباره بررسی شود.
- PII مثل آدرس و تلفن در لاگ عمومی، analytics و URL وارد نشود.
- برای چاپ، renderer سروری PDF/SVG بسازید و label را از داده تاییدشده بسازید.
- `1 of 2` برای هر package و tracking مستقل لازم است.
- reprint با شمارنده، کاربر، زمان و دلیل ثبت شود.
- تغییر آدرس بعد از چاپ باید سفارش را به review برگرداند و label قبلی را invalid کند.

## معیار پذیرش

- ادامه خرید بدون login کار می‌کند.
- تکمیل خرید بدون login به login/register داخلی هدایت می‌شود و cart حفظ می‌شود.
- آدرس کامل، تلفن، استان، شهر، پلاک/واحد و کدپستی ثبت می‌شود.
- روش ارسال و هزینه در checkout ثبت و به سفارش منتقل می‌شود.
- preview آدرس چاپی با داده فرم یکسان است.
- پنل admin همان snapshot را برای بسته و label مصرف می‌کند.
- مبلغ قابل پرداخت از server authority می‌آید.
- سفارش تکراری با retry یا callback ساخته نمی‌شود.
- مرجوعی و چندبسته‌ای به سفارش متصل و قابل audit هستند.
